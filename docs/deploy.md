# Deploying Terms on Render

One Render web service runs the API and serves the built web app; one Render Postgres holds the data.
Both are defined in [`render.yaml`](../render.yaml) (a Render Blueprint). Paid instances are used so the
service does not sleep while it is being judged.

## What the blueprint does

| Step       | Command                                                                                        |
| ---------- | ---------------------------------------------------------------------------------------------- |
| Build      | `corepack enable pnpm && pnpm install --frozen-lockfile --production=false && pnpm build:prod` |
| Pre-deploy | `pnpm db:deploy` (applies Prisma migrations before the new version serves)                     |
| Start      | `env NODE_ENV=production pnpm start` (`node apps/api/dist/server.js`)                          |
| Health     | `GET /api/health` (reports the database, PayPal and AI configuration)                          |

`pnpm build:prod` generates the Prisma client, then builds `@terms/shared`, the API and the web app
(typecheck, Vite build, production-bundle check). The server serves `apps/web/dist` for every path
outside `/api`, including `/offer/:token` and the PayPal return pages.

Checked locally (2026-11-11): the production build starts with `NODE_ENV=production`, the health check
reports the database as `ok`, and `/`, `/offer/:token` and `/client/vault/return` return the web app.
Not yet checked on Render itself: the `corepack enable pnpm` step and the first migration.

## First deploy (owner steps)

1. **Render account.** Sign up at render.com and add a payment method (paid instances).
2. **Connect GitHub.** In Render, connect the GitHub account and give the Render app access to the
   `Phantom-TA/terms` repository (it is private).
3. **Create the Blueprint.** New → Blueprint → choose the repository. Render reads `render.yaml` and
   asks for every variable marked `sync: false`:
   - `APP_BASE_URL`: leave a placeholder for now (you get the URL after the first deploy);
   - `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`: the sandbox app's credentials (the same as in `.env`);
   - `PAYPAL_WEBHOOK_ID`: leave empty for now;
   - `LLM_API_KEY`: optional; without it every AI role uses its deterministic mode;
   - `VITE_AG_GRID_LICENSE_KEY`, `VITE_AG_STUDIO_LICENSE_KEY`: from the web app's `.env`.
     `SESSION_SECRET` and `OFFER_TOKEN_SECRET` are generated by Render.
4. **Deploy.** The service deploys `develop` (manual deploys: `autoDeploy: false`). When it is live,
   note its URL, e.g. `https://terms.onrender.com`.
5. **Set the URL.** Set `APP_BASE_URL` to that URL (offer links and PayPal return URLs use it) and
   redeploy.
6. **Register the PayPal webhook.** From a checkout with the sandbox credentials in `.env`:

   ```bash
   pnpm webhook:register https://terms.onrender.com
   ```

   It prints `PAYPAL_WEBHOOK_ID=...`; set that on the service and redeploy. Running it again reuses the
   same registration. It also lists older registrations (the spikes' tunnels) to delete in the PayPal
   developer dashboard.

7. **Seed the demo.** From a checkout, point `DATABASE_URL` at the Render database's external URL and
   run `pnpm seed` (creates the scenario in Terms and as real sandbox invoices), then import:
   `POST /api/sync` as Maya Studio, or the Connect screen's "Import".
8. **Check.** `GET /api/health` shows `database: ok`, `paypalConfigured: true`; open the app, choose
   Maya Studio, and the Workbench shows the five demo invoices.

## Releasing

`develop` is merged into `main` only after the full demo passes end to end (Phase 9). Then change
`branch: develop` to `branch: main` in `render.yaml`, sync the Blueprint, and deploy.

## If the build cannot find pnpm

If `corepack enable pnpm` fails on Render, replace the start of the build command with
`npm install -g pnpm@12.6.0 &&` (the version in `package.json`'s `packageManager`).

## If the build fails installing `paypal`

The PayPal SDK is installed from GitHub and built during install with its own dev dependencies.
`NODE_ENV=production` must therefore not be a service environment variable (it would apply to the build
and make npm skip them: `tshy: not found`); `render.yaml` sets it only in the start command. If someone
added `NODE_ENV` under Environment in the dashboard, remove it there.
